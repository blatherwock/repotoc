Give a coding agent a table of contents for your Python code.

An agent in an unfamiliar repository spends much of its context reading source files just to learn what exists and where. RepoTOC writes that overview down: Markdown files that list every module, class, and function with its signature and docstring, laid out like the source tree. The agent starts at the root index, opens the module it needs, and reads source only when it has to.

The files are committed with the code, so people read and review them too. RepoTOC parses with the standard library ast module and never imports or runs your code.

uv add --dev git+https://github.com/blatherwock/repotoc then uv run repotoc

Source and docs on GitHub · MIT licensed

What it writes

RepoTOC writes one Markdown file for each Python file, in a folder tree that mirrors the source tree. Each directory also gets a repotoc_toc.md: an index of everything below it, with the first line of each docstring. Below, a small example package on the left and its output on the right.

arcade/checkers/players/minimax.py

"""A minimax player that searches a few plies deep.

The search alternates sides ply by ply and scores leaves with the
positional heuristic. Nothing is pruned; checkers trees stay small
enough for a demo.
"""

from typing import TYPE_CHECKING

from ..board import Board
from ..rules import legal_moves
from .heuristic import material, positional

if TYPE_CHECKING:
    from ...game import Move

_MAX_DEPTH = 4


class MinimaxPlayer:
    """A player choosing moves by minimax over a board heuristic.

    Attributes:
        side: The side this player moves for.
        depth: The search depth in plies.
    """

    def __init__(self, side: str, depth: int = _MAX_DEPTH) -> None:
        self.side = side
        self.depth = depth

    def choose(self, board: Board) -> "Move | None":
        """Return the move with the best minimax score, None if stuck."""
        best = None
        best_score = -999
        for move in legal_moves(board, self.side):
            score = self._search(_played(board, move), 1)
            if score > best_score:
                best_score = score
                best = move
        return best

    def _search(self, board: Board, ply: int) -> int:
        """Score a position recursively; higher is better for our side."""
        if ply >= self.depth:
            return positional(board, self.side)
        side = self.side if ply % 2 == 0 else _opponent(self.side)
        scores = [
            self._search(_played(board, move), ply + 1)
            for move in legal_moves(board, side)
        ]
        if not scores:
            return material(board, self.side)
        if ply % 2 == 0:
            return max(scores)
        return min(scores)


def _played(board: Board, move: "Move") -> Board:
    """Return a copy of the board with the move applied."""
    worked = Board(dict(board.pieces))
    worked.apply(move)
    return worked


def _opponent(side: str) -> str:
    """Return the other side's name."""
    return "light" if side == "dark" else "dark"

Pointing an agent at it

RepoTOC only writes files. To have an agent use them, add a short instruction to AGENTS.md or your tool's equivalent: 

Consult the table of contents under `docs/repotoc/` before searching or reading source files:
start at `docs/repotoc/repotoc_toc.md`, the linked outline of the whole repository with one-line
summaries, and open a module's doc file to survey its API before reading the source itself.

RepoTOC uses this on itself. See its AGENTS.md and the generated docs/repotoc.

Keeping it current

A stale table of contents misleads an agent, so RepoTOC is built to be regenerated often and checked in review:

  • A pre-commit hook regenerates the files on each commit that changes Python code.
  • repotoc --check exits nonzero when the files are out of date, for use in CI.
  • The same source always produces the same output, so a diff of the files shows only what changed in the code.

Settings such as source roots, output directory, and what to include live under [tool.repotoc] in pyproject.toml. See the README for the full list.

Compared with other tools

RepoTOC overlaps with three kinds of tools. It does a narrower job than each of them.

ToolsWhat they produceHow RepoTOC differs
Sphinx, MkDocs with mkdocstrings A documentation website for the users of a library. RepoTOC builds no site. Its output is read inside the repository by the people and agents working on the code. Use both if you publish docs.
lazydocs, pydoc-markdown Markdown API reference from docstrings. Closest in output. RepoTOC adds a linked index per directory with a one-line summary per entry, so a reader goes from the root to one function in a few steps. Unlike lazydocs, it never imports the code.
Aider's repo map, Repomix Context built for a model when it is needed: a ranked list of definitions (Aider) or the whole repository packed into one file (Repomix). RepoTOC output is a set of files on disk, not one prompt, so an agent reads only the parts it needs. It is committed and reviewed like code, and its text is the docstrings the authors wrote.

The first two groups work best when docstrings follow a structured style (Google, NumPy, or reST). RepoTOC asks for none. It writes each docstring as it is, and uses the first line as the summary in indexes. A member with no docstring is still listed.
